## 一、实习背景

本次实习以「用户管理系统」Web 应用为目标靶场，开展为期六天的全栈安全审计工作。目标系统基于 Python Flask 框架构建，集成了用户登录注册、信息搜索、头像上传、个人中心、充值、密码修改、动态页面加载、Ping 网络诊断等功能模块，涵盖了一款典型 Web 应用常见的功能场景。

本次实习的核心目标是：以一个存在大量安全漏洞的教学系统为载体，通过"漏洞发现→漏洞验证→漏洞修复→报告输出"的完整闭环，系统性地掌握 Web 安全渗透测试的方法论与实践技能。

## 二、实习主要内容

### 2.1 安全审计方法论

本次安全审计采用**白盒测试为主、黑盒测试为辅**的方式：

- **白盒测试**：审查应用源代码，识别不安全的编码模式（如 f-string 拼接 SQL、未过滤的用户输入、缺少安全配置等）
- **黑盒测试**：模拟真实攻击者，对运行中的服务进行端点探测、Payload 注入、权限绕过等攻击尝试
- **报告输出**：每轮审计均产出结构化的安全审计报告，包含漏洞原理、攻击复现、修复方案与验证结果

### 2.2 审计覆盖的主要安全域

#### 2.2.1 密码安全审计

对应用的身份认证机制进行了全面审计，发现并修复了多项密码安全问题：服务器密钥硬编码在源代码中，可被用于伪造会话Cookie；用户密码以明文形式存储在代码中，且登录验证直接进行字符串比对，未使用安全哈希算法；用户登录后密码在页面上明文回显，存在肩窥风险；此外，会话配置缺乏有效期限制和同源策略保护，增加了会话劫持的风险。针对上述问题，实施了密钥环境变量化、密码 bcrypt/scrypt 哈希存储与比对、关闭密码回显、配置会话安全属性等修复措施。

#### 2.2.2 SQL 注入审计

在注册和搜索功能中发现了四个 SQL 注入点。由于开发人员使用 f-string 将用户输入直接拼接到 SQL 语句中，攻击者可通过在输入框中提交单引号等特殊字符改变 SQL 语句结构，实现数据越权访问和敏感信息窃取。经测试验证，攻击者可利用 UNION 查询一次性提取数据库中的全部用户密码哈希，也可通过布尔盲注逐字符猜解数据。修复方案是将所有 SQL 操作替换为参数化查询，从根本上实现了数据与代码的分离。

#### 2.2.3 文件上传安全审计

头像上传功能在实现时未对上传文件做任何类型校验，导致存在严重的任意文件上传漏洞。攻击者可上传 HTML、PHP、JS、SVG 等各类恶意文件：HTML 文件可在用户浏览器中执行脚本实现存储型 XSS；PHP 文件若部署在支持 PHP 解析的服务器上可导致远程代码执行；SVG 文件由于可内嵌 JavaScript 同样存在 XSS 风险。此外还发现了文件覆盖覆盖、Content-Type 伪造、双扩展名绕过等攻击向量。修复方案构建了五层防御体系：扩展名白名单过滤、MIME 类型校验、魔术字节签名验证、文件覆盖保护和路径遍历防护。

#### 2.2.4 越权与业务逻辑审计

个人中心和充值功能存在严重的越权漏洞。个人中心的用户 ID 直接从 URL 参数获取，攻击者只需修改 URL 中的 user_id 参数即可查看任意用户的个人信息，且该接口完全不需要登录认证。充值功能同样存在问题——被充值的用户 ID 来自客户端表单数据，攻击者可修改表单中的 user_id 参数为他人充值或扣款。此外，充值金额未做正负校验和上限限制，攻击者可输入负数实现扣款，也可输入超大金额破坏经济系统。修复方案将所有敏感操作的 user_id 改为从服务端 Session 获取，并添加了金额的正负校验和上限控制。

#### 2.2.5 文件包含漏洞审计

动态页面加载功能在实现时直接将用户输入拼接到文件路径中，且未做任何路径校验。攻击者可通过 `../` 路径遍历读取服务器上的任意文件。经测试验证，攻击者可读取项目的源代码文件、系统用户密码文件、SSH 私钥、Git 仓库配置、进程环境变量等高度敏感信息。其中 SSH 私钥的泄露可直接导致服务器被完全接管。修复方案采用了三层防御：剥离路径分隔符防目录跳转、白名单限制仅允许特定页面名、利用文件真实路径校验确保文件在安全目录范围内。

#### 2.2.6 跨站请求伪造审计

密码修改接口在实现时使用了 `@csrf.exempt` 注解显式豁免了 CSRF 保护，同时该接口还存在多项越权问题：不需要验证原密码、不验证请求来源、用户名来自客户端表单可修改任意用户密码。攻击者只需诱导已登录的管理员访问一个恶意页面，该页面即可自动提交表单修改管理员的密码，从而实现账号接管。修复方案构建了六层防御体系：登录认证检查、CSRF Token 验证、请求来源同源检查、会话用户与操作用户一致性校验、原密码正确性验证、以及密码安全哈希存储。

#### 2.2.7 服务端模板注入审计

欢迎页和反馈功能使用 Flask 的 render_template_string 动态渲染模板，但开发人员使用 Python 的 f-string 将用户输入直接拼接到模板字符串中。由于 Jinja2 模板引擎会解析 `{{ }}` 语法的内容并作为 Python 表达式执行，攻击者可通过提交精心构造的 Payload 实现服务端模板注入。经测试验证，攻击者可执行任意算术运算、读取 Flask 应用配置密钥、通过 Python 内置函数读取服务器文件，甚至通过访问链获取 os 模块执行系统命令，实现远程代码执行。修复方案是将用户输入从 f-string 拼接改为通过模板变量传入，从根本上防止了用户输入被 Jinja2 解析为模板语法。

#### 2.2.8 命令注入审计

Ping 网络诊断功能为了实现 IP 连通性测试，将用户输入的 IP 地址通过 f-string 拼接到系统命令中，并使用 `shell=True` 参数通过系统 Shell 执行。由于 `shell=True` 会将命令字符串交给操作系统 Shell 解析，攻击者可在 IP 地址中注入 `;`（分号）、`|`（管道符）、`` ` ``（反引号）等 Shell 特殊字符来执行任意系统命令。经测试验证，三种注入方式均成功执行，攻击者可读取服务器敏感文件、泄露 SSH 私钥、执行任意系统命令。修复方案采用双层防御：IP 白名单正则校验确保输入为合法 IP 或域名格式，同时将命令执行方式从字符串传参改为列表传参以避免经过 Shell 解析。

## 三、实习总结

### 3.1 技术层面的收获

**深入理解 Web 漏洞根因。** 通过亲身参与漏洞发现到修复的全过程，深刻理解了大多数安全漏洞的根因是"数据与代码未分离"。无论是 SQL 注入中将用户输入拼入 SQL 语句、SSTI 中将用户输入拼入模板字符串，还是命令注入中将用户输入拼入系统命令，其本质都是将不可信的用户数据当作了可执行的代码来处理。理解了这一本质后，在面对不同类型的安全漏洞时能够迅速定位问题核心。

**建立防御纵深思维。** 在文件上传漏洞的修复中，单靠扩展名白名单是不够的，还需要配合 MIME 校验、魔术字节校验、路径防护等多层防御；在 CSRF 漏洞的修复中，仅靠 CSRF Token 不够，还需要 Referer 校验、身份校验、权限校验等多道防线。这种"纵深防御"的理念同样适用于其他安全场景——没有单一的防御措施是绝对可靠的，多层互补的防御体系才能提供真正的安全保障。

**掌握安全审计方法论。** 在实践中形成了"信息收集→漏洞识别→攻击验证→修复实施→回归测试→报告输出"的标准化工作流程，这一方法论可以推广应用于任何 Web 应用的安全审计工作。

### 3.2 安全意识的提升

**安全是设计出来的，不是事后补上去的。** 本次审计中发现的绝大多数漏洞，根源都可以追溯到开发阶段的安全意识缺失——使用 f-string 拼接 SQL 而不使用参数化查询、为了方便调试而留下 `@csrf.exempt`、为了快速实现功能而使用 `shell=True`。如果在架构设计阶段就建立安全编码规范，大部分高危漏洞完全可以避免。安全应该嵌入到软件开发生命周期的每个环节，而非等到上线前或发生事故后才进行补救。

**最小的攻击面，最大的安全性。** 每一行暴露给用户的代码、每一个用户可输入的参数，都可能成为攻击者的入口。文件上传功能如果不做类型校验，就相当于给攻击者开放了一个任意文件写入的通道；动态页面如果不做路径限制，就相当于给攻击者开放了一个任意文件读取的通道。每增加一个功能特性时，都应该同时评估其攻击面，并设计相应的安全控制措施。

### 3.3 职业发展的启示

这次实习让我认识到，网络安全不是某一个单一领域的知识，而是需要广泛涉猎的综合性学科。一个优秀的渗透测试人员既要了解 Web 开发框架的工作原理，又要熟悉操作系统和网络的底层机制，还要掌握密码学、认证授权、安全配置等多方面的知识。同时，安全审计工作不仅需要"发现问题的能力"，更需要"解决问题的方案思维"——不仅要找到漏洞在哪里，还要设计出在功能不受影响的前提下修复漏洞的最佳方案。

六天的安全审计实践让我收获的不仅仅是技术能力的提升，更是安全思维方式的养成。在未来的工作中，我将把"安全第一"的理念贯穿始终，为构建更加安全可靠的软件系统贡献力量。
